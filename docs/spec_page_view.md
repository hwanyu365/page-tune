# page-tune — 웹페이지 등록·Tune 적용 열람 (UC2)

## 1. 개요

| 항목 | 값 |
| --- | --- |
| 문서명 | spec_page_view |
| 작성자 | dohwan.ahn |
| 작성일 / 최종 수정일 | 2026-11-06 / 2026-11-08 |
| 버전 | 0.2 |
| 기준 커밋 ID | `2bdb848` |

- **기능명:** 웹페이지 등록·Tune 적용 열람 — 웹페이지를 Tune 과 묶어 등록하고, 열 때마다 Tune 을 적용해 본다.
- **목적 (Why):**
  - UC1 에서 만든 Tune 을 실제로 쓰는 경로다.
  - 열람 화면에 조작 UI 가 없다 → 뒤로가기를 누르면 이전 페이지가 아니라 화면이 닫히고, 새로고침·주소 공유·Tune 확인 수단이 없다.
  - Tune 을 고치려면 목록 → Tune 탭 → 편집 → 주소 재입력 → 저장 → 다시 열기를 거쳐야 한다.
  - 목록 카드가 제목·전체 주소·Tune 이름을 비슷한 글자로 나열해 어느 사이트인지 훑기 어렵다 [as-built]
  - 삭제는 확인 다이얼로그 뒤 바로 영구 삭제다 → 잘못 지우면 되살릴 수 없다 [as-built]
  - 처음 실행한 사용자는 Tune 과 웹페이지의 관계, 만드는 순서를 알 수 없다.
  - 하단 이전·다음 버튼 바가 화면 폭 전체를 64dp 높이로 계속 가린다 [as-built]
  - 열람 중 연결 오류는 WebView 기본 오류 페이지로, `mailto:`·`intent:` 링크는 알 수 없는 scheme 오류 페이지로 보이고, 다운로드 링크는 반응이 없다 → `shouldOverrideUrlLoading`·`onReceivedError`·`DownloadListener` 처리가 없다 [as-built]

## 2. 목표 및 범위

### In Scope

- 현재 동작(as-built): 웹페이지 목록·등록·편집·삭제, 열람 화면, Tune 적용(숨기기·색·시작 위치·이전/다음·두 번 탭), 마지막 주소 기억
- GH-18: 이 UC 화면의 문자열 리소스화와 한국어
- GH-19: 웹페이지 다이얼로그 제목 표시, 열람 화면 뒤로가기
- GH-20: 웹페이지 탭 빈 상태, 벡터 아이콘, 접근성 핵심
- GH-21: 색 적용의 불안정 id 처리, 숨기기의 유효하지 않은 셀렉터 처리
- GH-22: 열람 화면 빠른 메뉴, Tune 상태 표시, 열람 중 Tune 편집 후 즉시 반영
- GH-53: 목록 카드(도메인 아바타·호스트·Tune 칩·오버플로 메뉴), 길게 눌러 선택, 삭제 되돌리기, 시작 안내, 업데이트 후 새 소식. Tunes 탭 쪽 차이는 `spec_tune_edit.md` FR#1·FR#3·FR#30
- GH-55: 이전/다음 둥근 버튼과 자동 숨김, 로드 오류 화면, 외부 링크·다운로드 처리. 설정 화면은 `spec_settings.md`

### Out of Scope

- Tune 적용 범위를 URL·호스트로 제한하는 기능 → 현재처럼 이동한 모든 페이지에 적용된다 (§6.1)
- 다른 앱의 링크를 받아 여는 기능, 주소창 입력, 탭·히스토리
- 파비콘 → 소유자 결정(#51)으로 도메인 글자 아바타만 쓴다. 목록을 그리는 동안 네트워크 요청이 없다
- 이전/다음 버튼 위치 설정 → 설정 화면은 앱 정보·라이선스·처리방침만 둔다 (`spec_settings.md`)
- 내보내기·가져오기, Tune 적용 URL 패턴, 스와이프 이동, 글꼴·테마 설정, 홈 화면 바로가기 → 소유자 결정(#51)으로 하지 않는다
- 시작 안내를 다시 보는 메뉴

### 3.2 기능 요구사항

#### 웹페이지 목록 (Web Pages 탭)

- `FR#1` 목록은 최근 등록 순 카드다. 카드는 도메인 아바타·제목·호스트·Tune 칩을 보이고, 카드를 누르면 열람 화면을, 오버플로 메뉴의 편집을 누르면 편집 다이얼로그를 연다 [요구사항] GH-53 (순서·카드 탭 동작은 [as-built])
  - 아바타·호스트는 FR#24.
  - Tune 칩은 연결된 Tune 이름이다. 연결이 없거나 연결된 Tune 이 삭제됐으면 "Tune 없음" 칩을 보인다. 두 칩의 글자·배경 토큰은 `spec_design.md` §4.1 이다 → "흐림" 은 투명도가 아니라 보조 글자색으로 나타내 대비를 지킨다.
  - 오버플로 메뉴 항목은 편집, 삭제(FR#26)다.
  - 카드를 길게 누르면 선택 모드를 시작한다 (FR#3).
- `FR#2` 등록·편집 다이얼로그는 제목·주소·Tune(없음 포함)을 받는다 [as-built]. 주소는 §6.11 주소 입력 분류(U1~U5)를 통과한 http(s) 주소만 저장한다 [요구사항] GH-55

  ```
  Given 제목이나 주소가 비어 있다
  When  저장한다
  Then  저장하지 않고 모두 입력하라는 안내를 보인다
  ```

  - 주소에 scheme 이 없으면 `https://` 를 붙여 저장한다.
  - scheme 이 `http`·`https` 가 아니면(`file:`·`javascript:`·`content:` 등) 저장하지 않고 주소 칸에 입력 오류를 보인다.
  - [as-built] 은 `http://`·`https://` 로 시작하지 않는 입력 앞에 모두 `https://` 를 붙인다 (대소문자 구분) → `file:///x` 는 `https://file:///x` 로, `HTTPS://a` 는 `https://HTTPS://a` 로 저장된다.

  ```
  Given 등록 다이얼로그의 주소 칸에 javascript:alert(1) 을 넣었다
  When  저장한다
  Then  저장하지 않고 주소 칸에 http(s) 주소만 쓸 수 있다는 오류를 보인다
  ```
- `FR#3` 여러 개 삭제는 선택 모드에서 한다 [요구사항] GH-53 (툴바 삭제 진입·전체 선택·선택 없이 삭제 시 안내는 [as-built])
  - 진입: 카드를 길게 누르면 그 카드가 선택된 채로, 툴바 삭제를 누르면 아무것도 선택되지 않은 채로 시작한다.
  - 선택 모드 동안 상단에 선택 수, 전체 선택, 삭제, 닫기를 보인다. 선택 수는 선택이 바뀔 때마다 갱신한다.
  - 선택 수는 숫자만 보이고 삭제는 항상 아이콘으로 보인다 → 글꼴 200% 의 좁은 화면에서도 제목이 잘리지 않는다. 자리가 모자라면 전체 선택이 오버플로 메뉴로 간다 [요구사항] GH-68
  - 닫기·시스템 뒤로가기는 선택 모드를 끝낸다.
  - 삭제를 누르면 삭제할 개수를 묻는 확인 다이얼로그를 보이고, 확인하면 삭제한 뒤 FR#25 되돌리기를 보인다 (§6.6 D#9). 취소하면 선택 모드를 유지한다.

  ```
  Given 웹페이지 3개가 있다
  When  두 번째 카드를 길게 누른다
  Then  선택 모드가 시작되고 그 카드가 선택돼 있으며 선택 수가 1 이다
  ```
- `FR#23` 삭제 선택 모드에서 항목의 체크박스를 직접 탭해도 항목(카드)을 탭한 것과 같은 선택 상태가 된다. 구현과 TC 는 `spec_tune_edit.md` FR#23·TC#35·TC#36 과 같다 [요구사항] GH-37
- `FR#4` 다이얼로그 제목("웹페이지 추가" / "웹페이지 편집")이 배경과 구분돼 읽힌다 [요구사항] GH-19
- `FR#5` 웹페이지가 하나도 없으면 목록 자리에 설명 한 줄과 "웹페이지 추가" 행동 버튼을 보이고, 버튼은 등록 다이얼로그를 연다 [요구사항] GH-20

#### 목록 카드·삭제 되돌리기·시작 안내 (GH-53)

- `FR#24` 카드 왼쪽에 도메인 글자 아바타를, 제목 아래에 호스트를 보인다 [요구사항] GH-53
  - 글자·색·호스트 표기는 §6.7 의 함수 하나가 정한다 → 웹페이지·Tune 두 목록이 같은 규칙을 쓴다 (`spec_tune_edit.md` FR#1).
  - 파비콘을 가져오지 않는다 (Out of Scope).

  ```
  Given 주소가 https://www.example.org/news/1 인 웹페이지가 있다
  When  목록을 연다
  Then  아바타 글자는 E, 호스트 줄은 example.org 이고, 같은 호스트의 다른 카드와 아바타 색이 같다
  ```

- `FR#25` 삭제 직후 하단에 삭제한 개수와 "실행취소" 를 담은 스낵바를 보이고, 실행취소를 누르면 지운 항목을 삭제 전 상태로 되살린다 [요구사항] GH-53
  - 복원 범위·방식은 §6.8. Tune 의 규칙·웹페이지 연결 복원은 `spec_tune_edit.md` FR#30.
  - 스낵바는 5초 뒤 사라진다. API 29 이상에서는 접근성 설정의 권장 시간으로 늘린다 (FR#14 와 같은 기준).
  - 되돌리기 창은 스낵바가 사라질 때 닫힌다. 다음 삭제, 탭 전환(`spec_design.md` FR#7), 메인 화면을 떠남(다른 화면 열기·앱 전환)도 창을 닫는다.
  - 창이 닫힌 뒤에는 되살릴 수 없다. 창이 열린 동안 앱 프로세스가 끝나면 삭제가 그대로 남는다.

  ```
  Given 웹페이지 2개를 선택해 삭제했다
  When  스낵바의 실행취소를 누른다
  Then  두 웹페이지가 원래 위치에 같은 제목·주소·Tune 연결로 다시 보이고, 앱을 다시 실행해도 남아 있다
  ```

  ```
  Given 웹페이지 1개를 삭제해 스낵바가 떠 있다
  When  Tunes 탭으로 옮긴다
  Then  스낵바가 사라지고, Pages 탭으로 돌아와도 실행취소 수단이 없다
  ```

  ```
  Given 실행취소 시점에 스냅샷과 같은 id 의 행이 이미 있다
  When  복원한다
  Then  아무것도 쓰지 않고 되살리지 못했다는 안내를 보인다
  ```

- `FR#26` 오버플로 메뉴의 삭제는 그 카드 1개를 삭제하고 FR#25 되돌리기를 보인다 [요구사항] GH-53
  - FR#3 과 같은 확인 다이얼로그(1개)를 거친다 (§6.6 D#9).
- `FR#27` 처음 설치한 앱을 실행하면 메인 화면 위에 3장 이하의 시작 안내를 보인다 [요구사항] GH-53
  - "처음 설치" 의 판정과 업데이트 사용자 처리는 §6.13 의 순수 함수 하나가 한다 (FR#34 와 공유).
  - 내용: ① 사이트에서 요소를 골라 Tune 만들기 ② 웹페이지를 등록하고 Tune 연결하기 ③ 열람 중 빠른 메뉴로 Tune 켜기/끄기·편집하기.
  - 모든 장에 건너뛰기, 마지막 장에 시작하기를 둔다. 시스템 뒤로가기는 건너뛰기와 같다.
  - 건너뛰기·시작하기로 닫으면 그때의 versionCode 를 "마지막으로 본 버전" 으로 기록한다 → 같은 버전의 새 소식(FR#34)이 이어서 보이지 않는다.
  - 닫기 전에 프로세스가 끝나면 기록하지 않는다 → 다음 실행에 다시 보인다.
  - 기록은 SharedPreferences 의 정수 하나다 (§4, D#14).
  - 구현 PR 은 `docs/privacy.md` 의 "기기에 저장하는 정보" 와 `spec_store.md` §4 저장 행에 이 설정값을 추가한다 (`spec_store.md` FR#5).
  - 이 값은 Android 자동 백업 대상이다 → 백업에서 복원한 기기에서는 시작 안내가 보이지 않고, 복원한 기록보다 새 버전이면 FR#34 새 소식이 보인다.

  ```
  Given 앱을 처음 설치해 실행했다
  When  첫 장에서 건너뛰기를 누르고 앱을 다시 실행한다
  Then  시작 안내도 새 소식도 보이지 않는다
  ```

- `FR#34` 앱을 업데이트한 뒤 처음 실행하면 시작 안내 대신, 마지막으로 본 버전 이후 버전들의 변경 안내(새 소식)만 보인다 [요구사항] GH-53
  - 보여줄 버전은 §6.13 판정을 따른다. 그 사이에 변경 안내가 있는 버전이 없으면 아무것도 보이지 않고 기록만 현재 versionCode 로 바꾼다.
  - 기록이 없고 웹페이지·Tune 이 하나라도 있으면 이 기능 이전 버전(v1.1.1 이하)에서 업데이트한 사용자로 본다 → 시작 안내가 아니라 현재 버전까지의 새 소식을 보인다.
  - 새 소식은 다이얼로그 하나에 최신 버전부터 버전 이름과 변경 안내를 보이고, 확인·시스템 뒤로가기로 닫는다. 닫으면 현재 versionCode 를 기록한다. 닫기 전에 프로세스가 끝나면 다음 실행에 다시 보인다.
  - 변경 안내 문구는 버전마다 문자열 리소스(영어·한국어)에 두고, 변경 안내가 있는 versionCode 목록은 코드 상수 하나에 둔다. versionCode 는 `spec_release.md` 의 태그 규칙(`major*10000 + minor*100 + patch`)으로 만든다.
  - 변경 안내를 넣을 버전은 그 버전의 릴리스 전 PR 이 문구와 목록을 함께 추가한다. 넣지 않으면 그 버전은 표시 없이 기록만 바뀐다.
  - UX 2차 릴리스는 v1.2.0(versionCode 10200)이다. 10200 의 변경 안내 문구는 릴리스 전에 실제 반영 내용에 맞춰 확정한다 [요구사항] GH-53
  - 끝에서 당겨 이동(FR#36) 은 v1.3.0(versionCode 10300) 에 처음 나갔다. 10300 의 변경 안내 문구는 규칙 연결 방식(GH-79)에 맞춘다 [요구사항] GH-76, GH-79

  ```
  Given v1.1.1 에서 웹페이지 2개를 등록해 쓰던 사용자가 UX 2차 버전으로 업데이트했다
  When  앱을 실행한다
  Then  시작 안내가 아니라 UX 2차 버전의 새 소식이 보이고, 닫고 다시 실행하면 아무것도 보이지 않는다
  ```

  ```
  Given 마지막으로 본 버전이 A 이고, A 와 현재 버전 사이에 변경 안내가 있는 버전이 없다
  When  앱을 실행한다
  Then  아무것도 보이지 않고, 기록이 현재 버전으로 바뀐다
  ```

  - 연결은 편집 화면의 저장 트랜잭션이 한다 (`spec_tune_edit.md` FR#21). 저장하고 돌아오면 열람 화면은 웹페이지와 Tune 을 DB 에서 다시 읽어 FR#18 과 같이 바로 적용한다.
  - 취소하고 돌아오면 Tune 을 만들지도 연결하지도 않는다.

  ```
  Given Tune 이 연결되지 않은 웹페이지를 보고 있다
  When  이 페이지에 Tune 만들기 → 숨기기 하나 추가 → 저장하고 돌아온다
  Then  그 요소가 숨겨져 있고, 웹페이지 목록에 새 Tune 이름이 연결돼 보인다
  ```

- `FR#20` 열람 화면에 들어오거나 Tune 을 켜고 끌 때 Tune 상태를 잠깐 보인다 [요구사항] GH-22
  - 켜진 상태: 저장된 규칙 수를 종류별(숨기기·색상·이전/다음 이동·시작 위치)로 보이고, 0개인 종류는 생략한다.
  - 연결된 Tune 의 규칙이 0개면 규칙이 없다는 표시를 보인다.
  - 끈 상태: Tune 이 꺼졌다는 표시만 보인다.
  - 연결된 Tune 이 없으면 진입 시 표시하지 않는다.
  - 표시는 이전/다음 버튼을 가리지 않는다.

#### 로드 오류·외부 링크 (GH-55)

- `FR#29` 주 문서 로드가 실패하면 WebView 위에 오류 화면을 보인다 [요구사항] GH-55
  - 종류별 제목·설명은 §6.10 분류를 따른다.
  - 다시 시도는 실패한 주소를 다시 로드한다. 로드가 끝나면 오류 화면이 사라진다.
  - 오류 화면 동안 이전/다음 버튼과 두 번 탭은 동작하지 않는다. 빠른 메뉴는 쓸 수 있다.
  - 하위 리소스(이미지·스크립트·iframe) 실패와 HTTP 4xx/5xx 응답에는 오류 화면을 띄우지 않는다 → 사이트가 보낸 페이지를 그대로 보인다.
  - Safe Browsing 경고는 WebView 기본 화면을 그대로 쓴다.

  ```
  Given 기기가 오프라인이다
  When  웹페이지를 열고, 연결을 복구한 뒤 다시 시도를 누른다
  Then  처음에는 연결할 수 없다는 오류 화면이, 다시 시도 후에는 페이지가 보인다
  ```

- `FR#30` 인증서(SSL) 오류는 항상 로드를 중단하고, 무시하고 진행하는 수단을 두지 않는다 [요구사항] GH-55 (중단 자체는 WebView 기본 처리 [as-built])
  - 주 문서의 인증서 오류면 FR#29 오류 화면의 보안 연결 종류를 보인다. 하위 리소스의 인증서 오류는 표시 없이 막는다.
  - 주 문서 여부는 §6.10 의 S1~S3 로 판정한다 → 다른 호스트로 리다이렉트된 대상의 인증서 오류도 오류 화면이 된다. 하위 리소스로 확정할 수 없으면 오류 화면 쪽으로 판정한다.
  - 근거는 §6.6 D#13.

  ```
  Given 인증서가 만료된 https 사이트를 등록했다
  When  열람한다
  Then  보안 연결 오류 화면이 보이고, 페이지로 진행하는 버튼이 없다
  ```

- `FR#31` 페이지가 다른 주소로 이동하려 할 때마다 §6.11 분류로 WebView 에 열지, 다른 앱에 넘길지, 막을지 정한다 [요구사항] GH-55
  - 편집 화면 WebView 도 같은 분류를 쓴다 (`spec_tune_edit.md` FR#29).
  - "외부 앱으로 열까요?" 확인 창은 무엇을 여는지 보인다 [요구사항] GH-55
    - intent: 앱 이름(설치된 앱 라벨을 읽을 수 있으면 라벨, 아니면 package) + 앱에 넘길 data 주소(있을 때) + 설치돼 있지 않을 때의 대체 주소 또는 "아무것도 열리지 않음". package 가 없으면 data 주소, 둘 다 없으면 "알 수 없는 앱".
    - 근거(리드 결정 2026-11-08): 앱 이름만 보이면 사용자가 허락하는 대상(앱)과 실제로 넘어가는 내용(data)이 다르다 → 둘을 함께 보여 일치시킨다.
    - `mailto:` 는 받는 주소, `tel:` 은 번호, 그 밖 scheme 은 주소 전체.
    - 80자를 넘으면 79자 + `…` 로 자른다 → 긴 주소가 버튼을 화면 밖으로 밀지 않는다.
    - 앱 라벨은 `<queries>` 없이 읽으므로 Android 11 이상에서는 대부분 package 로 보인다 [NFR#6].
  - 확인 창이 이미 떠 있으면 새 요청은 버린다. 화면이 끝나는 중(`isFinishing`·`isDestroyed`)이면 띄우지 않는다 [요구사항] GH-55
    - 근거: 새 요청으로 바꾸면 사용자가 보고 있던 대상이 누르기 직전에 다른 대상으로 바뀔 수 있다. 버리면 창은 하나이고 내용은 사용자가 본 그대로다. 끝나는 화면에 창을 띄우면 창 누수가 난다.
  - 새 창 요청(`target="_blank"`, `window.open`)은 새 창을 만들지 않고 현재 WebView 의 이동으로 처리한다 → 같은 분류를 거친다 (§6.11 새 창, D#19).
  - 앱이 `loadUrl` 로 직접 여는 주소(저장된 주소, 편집 화면의 테스트 주소·로드 주소, 다시 시도)는 이 링크 분류를 거치지 않는다 → 대신 입력할 때와 열 때 모두 §6.11 주소 입력 분류(U1~U5)를 거친다 (FR#2, FR#35, `spec_tune_edit.md` FR#5·FR#11·FR#20).
  - 다른 앱에 주소를 넘기는 것은 새 전송 경로다 → 구현 PR 은 `docs/privacy.md` "공유" 절에 "사용자가 누른 메일·전화·앱 링크와 다운로드 주소는 해당 앱에 넘긴다" 를 추가한다 (`spec_store.md` FR#5). 설정 화면의 처리방침 열기(`spec_settings.md` FR#3)도 같은 절이 덮는다.

  ```
  Given 페이지에 mailto: 링크가 있다
  When  사용자가 그 링크를 누른다
  Then  "외부 앱으로 열까요?" 확인이 보이고, 열기를 고르면 메일 앱(또는 앱 선택 창)이 열리고 열람 화면은 그대로다
  ```

  ```
  Given 버튼의 클릭 처리기가 location 을 intent: 주소로 바꾼다
  When  사용자가 그 버튼을 누른다
  Then  "외부 앱으로 열까요?" 확인이 보이고, 취소하면 아무것도 열리지 않는다
  ```

  ```
  Given 광고 iframe 이 사용자 조작 없이 intent: 주소로 이동한다
  When  페이지를 보고 있다
  Then  다른 앱이 열리지 않고 페이지도 바뀌지 않는다
  ```

  ```
  Given 페이지의 https 링크가 서버 302 로 market: 주소에 리다이렉트된다
  When  사용자가 그 링크를 누른다
  Then  "외부 앱으로 열까요?" 확인이 보이고, 열기를 고를 때만 스토어 앱이 열리며 취소하면 페이지가 그대로다 (L7)
  ```

  ```
  Given 페이지에 file:///sdcard/ 링크가 있다
  When  사용자가 누른다
  Then  아무것도 열리지 않는다
  ```

- `FR#35` 열람 화면은 저장된 주소를 열기 전에 §6.11 주소 입력 분류를 다시 적용하고, 통과하지 못하면 열지 않고 FR#29 오류 화면의 "열 수 없는 주소" 종류를 보인다 [요구사항] GH-55
  - 저장된 데이터는 지우거나 고치지 않는다 → 사용자가 편집 다이얼로그에서 고칠 수 있다.
  - 이 경우 다시 시도 버튼은 두지 않는다 → 같은 주소는 다시 시도해도 같은 결과다.
  - 근거: [as-built] 저장분과 백업에서 복원한 DB 에는 입력 분류를 거치지 않은 주소가 있을 수 있다.

  ```
  Given DB 에 주소가 content://x 인 웹페이지가 있다
  When  그 웹페이지를 연다
  Then  WebView 에 로드하지 않고 열 수 없는 주소 오류 화면을 보이며, 웹페이지 행은 그대로 남는다
  ```

- `FR#32` `intent:` 주소는 §6.11 의 허용 필드만으로 새 Intent 를 만들어 넘긴다. 열 앱이 없으면 http(s) 대체 주소를 WebView 에 열고, 대체 주소도 없으면 열 수 있는 앱이 없다는 안내를 보인다 [요구사항] GH-55

  ```
  Given intent 주소가 component 와 extra 를 지정하고, 지정한 package 가 설치돼 있지 않으며, browser_fallback_url 이 https 주소다
  When  사용자가 그 링크를 누른다
  Then  지정한 component 는 열리지 않고 대체 주소가 열람 WebView 에 열린다
  ```

- `FR#33` 다운로드가 시작되면 파일 주소를 §6.11 다운로드 분류(W1~W2)로 나눈다. http(s) 주소면 "브라우저에서 열기" 버튼이 있는 스낵바를 보이고, 사용자가 그 버튼을 누를 때만 외부 브라우저로 넘긴다 (`ACTION_VIEW` + `CATEGORY_BROWSABLE`, §6.6 D#16) [요구사항] GH-55
  - 그 밖 scheme(`blob:`·`data:`·`file:`·`content:`·`ftp:` 등)과 해석할 수 없는 주소는 넘기지 않고 지원하지 않는다는 안내를 보인다.
  - 스낵바는 FR#25 와 같은 시간 기준으로 사라진다. 새 다운로드가 오면 이전 스낵바를 대체한다.
  - 버튼이 넘기는 주소는 분류를 통과한 그 주소 그대로다.
  - 로그인 쿠키는 넘어가지 않는다 → 로그인이 필요한 파일은 브라우저에서 다시 로그인해야 받을 수 있다.
  - 열 앱이 없으면 열 수 있는 앱이 없다는 안내를 보인다 (§6.11 L10 과 같다).

  ```
  Given 광고 iframe 이 사용자 조작 없이 첨부 파일 응답(`Content-Disposition: attachment`)을 만든다
  When  페이지를 보고 있다
  Then  외부 브라우저가 열리지 않고, 스낵바의 "브라우저에서 열기" 를 누를 때만 열린다
  ```

  ```
  Given 다운로드 주소가 file:///sdcard/a.apk 다
  When  다운로드가 시작된다
  Then  다른 앱에 넘기지 않고 지원하지 않는다는 안내만 보인다
  ```

## 6. 동작 로직 및 정책

### 6.1 Tune 적용 시점 [FR#7] [FR#8]

- 규칙은 화면을 열 때 한 번 읽는다. 편집에서 저장하고 돌아올 때(FR#18, FR#19)만 다시 읽는다.
- 로드가 끝날 때마다 현재 주소·호스트와 상관없이 적용한다 [as-built]
  - 외부 호스트로 이동해도 같은 Tune 이 적용된다 → 범위 제한은 Out of Scope.
- 색은 `<style>` 태그 한 개에 규칙을 모아 넣는다 → 나중에 추가된 노드에도 CSS 로 적용되고 재적용 루프가 필요 없다.
  - 규칙은 `셀렉터, 셀렉터 * { 선언 !important; }` 형태 → 자식이 자기 색을 가진 경우까지 덮는다.
- 시작 위치는 목표 y 에 닿을 때까지 100ms 간격으로 최대 20회 시도하고, 사용자가 화면을 만지면 멈춘다 → 로드 직후에는 본문이 짧아 스크롤이 잘린다.
- Tune 을 끈 상태(FR#16)에서는 위 적용을 모두 건너뛰고 이전/다음 버튼과 두 번 탭을 끈다.

### 6.3 마지막 주소 기억 [FR#11]

- 원래 호스트는 화면을 열 때 저장 주소에서 구한다.
- Cloudflare 확인 페이지 주소를 저장하면 다음에 확인 페이지부터 열린다 → 해당 호스트는 저장하지 않는다.

### 6.4 뒤로가기 [FR#13]

- 시스템 뒤로가기는 가로채지 않고 플랫폼 기본 동작(화면 닫기)에 맡긴다 → 이전/다음 이동으로 쌓인 히스토리를 하나씩 되돌리지 않고 한 번에 목록으로 나간다.
- 이전 페이지 이동은 빠른 메뉴 '뒤로'가 WebView 히스토리로 직접 처리한다.
- 뒤로 간 페이지도 FR#11 에 따라 저장 주소가 된다 → "마지막으로 본 위치" 의미와 맞다.

### 6.5 편집 왕복 [FR#17] [FR#18]

- `testUrl` 은 Tune 의 대표 페이지다 → 열람 중 들어간 개별 글 주소로 덮어쓰지 않는다. 보장 방식은 `spec_tune_edit.md` §4.4.
- 저장 후 다시 로드하는 이유: 이미 적용된 숨기기는 인라인 스타일이라 규칙을 지운 경우 다시 로드해야 원래대로 보인다.

### 6.8 삭제와 되돌리기 [FR#3] [FR#25] [FR#26]

DB 연쇄 [as-built]

| 지우는 것 | 함께 지워지는 것 | 남는 것 | 근거 |
| --- | --- | --- | --- |
| 웹페이지 | 없음 | — | `webpages` 를 참조하는 FK 가 없다 |
| Tune | 그 Tune 의 `plugin_actions` 전부 | 그 Tune 을 가리키는 `webpages.pluginId` | `plugin_actions.pluginId` FK 가 `ON DELETE CASCADE` 이고 Room 생성 코드가 연결마다 `PRAGMA foreign_keys = ON` 을 켠다. `webpages.pluginId` 는 FK 가 없다 (`app/schemas/` v5) |

- 지워진 Tune 을 가리키는 `pluginId` 는 목록·열람에서 Tune 없음으로 보인다 (FR#1, FR#7) [as-built].

복원 범위 [요구사항] GH-53

- 웹페이지: 지운 행을 같은 `id`·`title`·`url`·`pluginId` 로 다시 넣는다.
- Tune: Tune 행과 규칙 행을 같은 `id` 와 모든 컬럼으로 다시 넣는다. 웹페이지 연결은 쓰지 않는다 → 남아 있던 `pluginId` 가 같은 `id` 의 Tune 을 다시 가리킨다 (`spec_tune_edit.md` FR#30).
- 같은 `id` 로 넣는 근거
  - 세 테이블의 `id` 는 `AUTOINCREMENT` 다 (`app/schemas/` v5) → 지운 뒤 새로 만든 행이 그 `id` 를 받지 않아 충돌하지 않는다.
  - 목록은 `id` 역순이다 → 같은 `id` 면 원래 위치로 돌아온다.
  - 규칙은 Tune 안 순서가 의미를 갖는다 (`spec_tune_edit.md` §6.4) → 같은 `id` 면 순서가 보존된다.

실행 규칙 [요구사항] GH-53

- 삭제는 스냅샷 읽기와 삭제를 한 트랜잭션으로 한다 → 스냅샷이 실제로 지운 행과 같다.
- 복원은 한 트랜잭션이다 → 일부만 되살아난 상태가 남지 않는다.
- 복원 쓰기는 같은 `id` 가 있으면 실패하는 삽입이다. 하나라도 실패하면 전체를 되돌리고 안내한다 (FR#25).
- id 목록을 받는 읽기·삭제·충돌 조회는 900개씩 나눠 같은 트랜잭션 안에서 호출한다 [요구사항] GH-53
  - 근거: minSdk 24~35 의 SQLite 바인딩 변수 상한이 999 다 → 전체 선택으로 그보다 많이 지우면 `IN (:ids)` 가 실패한다.
- 삭제가 실패하면 아무것도 지우지 않고(트랜잭션 되돌림) 삭제하지 못했다는 안내를 보인다 [요구사항] GH-53
  - 근거: 현재 DAO 의 삽입은 `REPLACE` 다 [as-built] → `plugins` 에 `REPLACE` 를 쓰면 기존 행을 지웠다 다시 넣으면서 CASCADE 로 그 Tune 의 규칙까지 지운다.
- 구조는 `spec_tune_edit.md` §6.10 과 같은 세 부분이다: 복원 계획 함수(스냅샷 → 쓸 행 목록, 순수), 실행 함수(저장소 인터페이스의 트랜잭션 블록 한 번), Room 어댑터.

되돌리기 창 동안 연결이 바뀌는 경로

- 웹페이지 편집 다이얼로그는 지워진 Tune 을 고를 수 없어 저장하면 `pluginId` 가 `null` 이 된다 [as-built] → 연결이 끊긴 뒤 Tune 을 되살리면 연결이 돌아오지 않는다.
- Tunes 탭의 스낵바가 떠 있는 동안 웹페이지 다이얼로그를 열려면 탭을 옮겨야 하고, 탭 전환은 창을 닫는다 (FR#25) → 창 안에서 이 경로가 생기지 않는다.
- 열람·편집 화면을 여는 것도 메인 화면을 떠나는 것이라 창을 닫는다.

### 6.9 페이지 맨 아래 판정 [FR#28]

- 남은 아래 거리 = 문서 높이 × 배율 − (스크롤 위치 + WebView 높이). 화면 밀도로 dp 로 바꾼다 → 기기마다 같은 거리에서 바뀐다.
- 남은 아래 거리가 24dp 이하면 맨 아래다. 음수(문서가 화면보다 짧음)도 맨 아래다.
- 문서 높이가 아직 0 이면(그려지기 전) 맨 아래가 아니다 → 로드 직후 판정이 읽기 전에 버튼을 띄우지 않는다.
  - 로드 완료 직후 문서 높이가 0 이면 200ms 간격으로 최대 10번 다시 판정한다 → 높이가 생겨도 알려 주는 이벤트가 없어, 스크롤할 수 없는 짧은 페이지가 버튼을 못 받는 일을 막는다.
- 문서가 지연 로드로 늘어나도 다음 스크롤 때 다시 판정한다 → 맨 아래에 머문 채 늘어나면 스크롤 전까지 버튼이 남는다.
- 페이지 로드가 시작되면 맨 아래가 아니다 → 다음 페이지를 불러오는 동안 이전 페이지의 버튼이 남지 않는다. 로드 완료 직후 다시 판정한다 (FR#28).

### 6.10 로드 오류 분류 [FR#29] [FR#30]

순수 함수가 (WebViewClient 오류 코드, 주 문서 여부) → 오류 종류 또는 없음을 만든다. 편집 화면도 같은 함수를 쓴다 (`spec_tune_edit.md` FR#28).

| 입력 | 종류 | 안내 요지 |
| --- | --- | --- |
| 주 문서가 아님 | 없음 | 오류 화면을 띄우지 않는다 |
| `ERROR_HOST_LOOKUP` | 연결할 수 없음 | 인터넷 연결과 주소를 확인 (D#17) |
| `ERROR_CONNECT`, `ERROR_TIMEOUT`, `ERROR_IO` | 서버 응답 없음 | 잠시 뒤 다시 시도 |
| `ERROR_FAILED_SSL_HANDSHAKE`, 주 문서의 `onReceivedSslError` | 보안 연결 오류 | 사이트 인증서 문제, 진행 수단 없음 (FR#30) |
| `ERROR_BAD_URL`, `ERROR_UNSUPPORTED_SCHEME` | 열 수 없는 주소 | 주소 확인 |
| 그 밖 | 페이지를 열 수 없음 | 다시 시도 |

- 주 문서 판정은 `WebResourceRequest.isForMainFrame` 이다.
- `onReceivedSslError` 는 요청 정보가 없다 → 순수 함수가 (오류 주소, 주 문서 주소 집합, 주 문서 커밋 여부) → 주 문서 / 하위 리소스를 정한다 (S1~S3).

| 조건 | 입력 | 판정 | 근거 |
| --- | --- | --- | --- |
| S1 | 오류 주소가 이번 로드의 주 문서 주소 집합에 있다 | 주 문서 | 집합 = 로드를 시작한 주소 + 주 프레임 리다이렉트로 거친 주소 (`onPageStarted`, 주 프레임 `shouldOverrideUrlLoading`) → 다른 호스트로 리다이렉트된 대상의 인증서 오류도 잡는다 |
| S2 | 이번 로드의 주 문서가 아직 커밋되지 않았다 (`onPageCommitVisible` 전) | 주 문서 | 리다이렉트 주소가 어느 콜백으로도 오지 않는 경우에 대비해, 하위 리소스로 확정할 수 없으면 오류 화면 쪽으로 판정한다 |
| S3 | 그 밖 | 하위 리소스 | 주 문서가 이미 그려진 뒤의 오류다 |

- 어느 판정이든 `cancel()` 은 항상 부른다 (§6.12) → 판정은 화면 표시만 정한다.
- S2 의 한계: 주 문서 커밋 전에 하위 리소스의 인증서 오류가 오면 오류 화면이 뜰 수 있다 → 다시 시도로 회복하고, 보안상 안전한 쪽으로 틀린다.
- 집합과 커밋 여부는 새 주 문서 로드(`loadUrl`, 다시 시도, 링크 이동)가 시작될 때 초기화한다.
- `WebViewClient.ERROR_*` 는 컴파일 시 정수 상수로 들어간다 → 분류 함수를 JVM 단위 테스트로 실행할 수 있다.
- HTTP 4xx/5xx 는 오류가 아니라 응답이다 → `onReceivedHttpError` 로 오류 화면을 띄우지 않는다.

### 6.11 링크 분류와 intent 구성 [FR#31] [FR#32] [NFR#5]

순수 Kotlin 함수다. `android.net.Uri`·`Intent.parseUri` 를 쓰지 않는다 → JVM 단위 테스트로 조건마다 고정한다. scheme 은 대소문자를 구분하지 않는다.

링크 분류 (위에서부터 처음 맞는 조건)

| 조건 | 입력 | 결정 | 근거 |
| --- | --- | --- | --- |
| L1 | scheme 을 구할 수 없음 | 막기 | 해석할 수 없는 주소를 WebView·다른 앱에 넘기지 않는다 |
| L2 | `http`, `https` | WebView | |
| L3 | `about:blank`, `about:srcdoc` | WebView | 사이트가 빈 창·프레임을 여는 데 쓴다 |
| L4 | `javascript` `data` `file` `content` `blob` `filesystem` `about`(L3 밖) `chrome` `view-source` | 막기 | `file`·`content` 는 기기 파일·다른 앱 데이터를 앱 WebView 에 연다. 나머지는 페이지가 만든 문서·브라우저 내부 화면을 최상위 문서로 연다 |
| L5 | L2~L4 밖 scheme 인데 주 프레임이 아님 | 막기 | 광고 iframe 이 사용자 모르게 다른 앱·스토어를 연다 |
| L6 | L2~L4 밖 scheme 인데 사용자 제스처(`hasGesture`)도 서버 리다이렉트(`isRedirect`)도 아님 | 막기 | 사용자 조작 없는 이동으로 다른 앱이 열리는 것을 막는다 |
| L7 | L2~L4 밖 scheme, 제스처 있음 또는 리다이렉트 | L8·L9 의 결과를 "외부 앱으로 열까요?" 확인 후 연다. L8 이 막기면 확인 없이 막기 | 실측상 리다이렉트는 제스처 없음으로, 클릭 처리기 안 스크립트 이동은 제스처 있음으로 온다 → 어느 쪽도 사용자가 고른 앱인지 알 수 없어 항상 확인한다 (D#12). 취소하면 아무것도 하지 않는다 |
| L8 | `intent` (`intent:` 와 `intent://` 모두) | I1~I7 의 결과 | |
| L9 | `market` 및 그 밖 scheme (`mailto` `tel` `sms` 앱 전용 scheme) | 외부 앱 대상: `ACTION_VIEW` + `CATEGORY_BROWSABLE`, data = 원래 주소, component 없음 | 시스템이 웹 링크로 열 수 있다고 선언한(browsable) 화면만 고른다 |
| L10 | 외부 앱 실행이 `ActivityNotFoundException` 으로 실패 | intent 면 I6 대체 주소, 아니면 열 수 있는 앱이 없다는 안내 | 미리 조회하지 않는다 [NFR#6]. 어댑터 동작이라 단위 범위 밖 (NFR#5) |

다운로드 분류 (`DownloadListener` 진입, FR#33)

| 조건 | 입력 | 결정 | 근거 |
| --- | --- | --- | --- |
| W1 | L1 과 같은 방법으로 구한 scheme 이 `http`·`https` (대소문자 무시) | "브라우저에서 열기" 스낵바 | 외부 브라우저가 받을 수 있는 주소만 넘긴다 |
| W2 | 그 밖 (scheme 없음, L4 목록, `ftp` 등) | 지원하지 않는다는 안내 | `file`·`content` 를 넘기면 기기 파일·다른 앱 데이터를 다른 앱이 열게 된다. `blob`·`data` 는 이 WebView 안에서만 의미가 있다 |

- 다운로드 분류는 링크 분류와 scheme 해석을 공유한다 → 두 진입점의 대소문자·공백 처리가 어긋나지 않는다.
- 제스처 대신 스낵바 버튼으로 사용자 조작을 만든다 (D#16) → 순수 함수의 입력은 주소 하나다.

새 창 (`target="_blank"`, `window.open`)

[as-built] 두 WebView 모두 `setSupportMultipleWindows` 를 부르지 않아 기본값 `false` 이고, `WebChromeClient.onCreateWindow` 를 구현하지 않으며, `javaScriptCanOpenWindowsAutomatically` 는 `true` 다 (`WebViewConfig`) → 새 창 요청이 현재 WebView 의 이동이 된다.

| 조건 | 요구 | 근거 |
| --- | --- | --- |
| N1 | `setSupportMultipleWindows(true)` 를 두지 않고 `onCreateWindow` 를 구현하지 않는다 | 새 창 요청이 현재 WebView 의 일반 이동이 되어 `shouldOverrideUrlLoading` 의 L1~L9 을 거친다 → 새 창 전용 분류 경로를 따로 만들지 않는다 (D#19) |
| N2 | `javaScriptCanOpenWindowsAutomatically` 를 `false` 로 바꾼다 | 사용자 조작 없는 `window.open` 을 WebView 가 막는다 → 팝업 광고가 보던 페이지를 바꾸지 못한다. 사용자 클릭 안의 `window.open` 은 그대로 열린다 |

주소 입력 분류 (앱이 `loadUrl` 로 여는 주소의 저장·로드 전, FR#2·FR#35, `spec_tune_edit.md` FR#5·FR#11·FR#20)

순수 함수가 입력 문자열 → http(s) 주소 또는 입력 오류를 만든다. 위에서부터 처음 맞는 조건이다.

| 조건 | 입력 | 결과 | 근거 |
| --- | --- | --- | --- |
| U1 | 앞뒤 공백을 자른 값이 비어 있음 | 입력 오류 | |
| U2 | `영문자[영문자·숫자·+·.·-]*:` 로 시작하고 `:` 뒤가 숫자 포트(`:숫자` 뒤에 `/`·끝)가 아님 → scheme 있음. scheme 이 `http`·`https` (대소문자 무시) | 허용. scheme 은 소문자로 바꾼다 | W1 과 같은 scheme 해석 |
| U3 | scheme 있음, 그 밖 scheme | 입력 오류 | `file`·`content`·`javascript`·`data` 등 L4 목록과 외부 앱 scheme 을 `loadUrl` 로 열지 않는다 |
| U4 | scheme 없음 (`example.com`, `localhost:8080/x`) | `https://` 를 붙여 허용 | [as-built] 의 보정을 유지한다. 포트 예외가 없으면 `localhost:8080` 이 scheme `localhost` 로 거부된다 |
| U5 | U2·U4 결과의 호스트가 비어 있음 (`https://`, `https:///a`) | 입력 오류 | 열 곳이 없는 주소를 저장하지 않는다 |

- 허용 결과는 같은 입력을 다시 넣어도 같다 → 이미 정규화된 저장 주소(`testUrl` 포함)는 열 때 다시 분류해도 바뀌지 않는다.
- http(s) 만 허용하는 것은 소유자 승인 (2026-11-08).
- `WebView.loadUrl` 은 앱 소스 전체에서 래퍼 한 곳에서만 부른다 (U6) [요구사항] GH-55
  - 래퍼는 주소 입력 분류를 먼저 적용하고, 통과한 정규화 주소만 `loadUrl` 에 넘긴다. 통과하지 못하면 호출부가 준 거부 처리(입력 오류·열 수 없는 주소 표시)를 부른다.
  - 대상 호출: 열람 화면의 저장 주소 열기, 편집 화면의 새 Tune 로드 주소·불러오기·기존 Tune 진입 (as-built 의 `loadUrl` 4곳), intent 대체 주소 열기(FR#32).
  - 대체 주소가 분류에서 거부되면 아무것도 열지 않고 FR#32 의 "열 수 있는 앱이 없어요" 안내를 보인다.
  - 근거: 호출 지점마다 분류를 넣으면 새 호출이 생길 때 빠뜨려도 드러나지 않는다 → 한 곳으로 모으면 "그 밖에 `loadUrl` 이 없다" 하나로 검사된다.
  - `reload()` 는 이미 연 주소를 다시 여는 것이라 래퍼 밖에 둔다.

- WebView 결정은 `shouldOverrideUrlLoading` 이 `false` 를 돌려 WebView 가 그대로 연다. 외부 앱·막기는 `true` 를 돌린다.
- 막기는 안내 없이 아무것도 하지 않는다 → 자동 시도가 반복돼도 화면이 어지럽지 않다.

intent 구성 (`intent://나머지#Intent;키=값;…;end`)

| 조건 | 처리 | 근거 |
| --- | --- | --- |
| I1 | `#Intent;` 로 시작해 `;end` 로 끝나는 부분이 없으면 막기 | 형식이 아닌 입력을 추측해 해석하지 않는다 |
| I2 | 쓰는 키는 `scheme`, `package`, `S.browser_fallback_url` 셋뿐이다. action 은 항상 `ACTION_VIEW`, category 는 `CATEGORY_BROWSABLE` 하나 | 허용 목록 (D#18) |
| I3 | `component`, `SEL`(selector), `action`, `category`, `launchFlags` 와 그 밖 extra(`S.` `i.` `l.` `B.` 등, I2 의 하나 제외) 는 읽지 않는다 | 페이지가 비공개 화면·selector·extra 로 다른 앱의 내부 동작을 부르는 것(intent scheme hijacking)을 막는다 |
| I4 | data = `scheme 값` + `:` + `intent:` 뒤부터 `#Intent;` 앞까지 (`intent://a/b` → `scheme://a/b`, `intent:a@b` → `scheme:a@b`). `scheme` 키가 없으면 data 없음 | Chrome `Intent.parseUri` 의 intent 주소 형식. 슬래시 없는 형에 `//` 를 새로 붙이지 않는다 |
| I5 | `scheme` 값이 L4 목록이거나 `package` 가 이 앱 id 면 막기 | data 로 L4 를 우회하거나, 페이지가 이 앱 화면을 여는 경로를 막는다 |
| I6 | 대체 주소는 퍼센트 디코딩 후 scheme 이 `http`·`https` 일 때만 쓴다. 그 밖이면 대체 주소 없음 | 대체 주소로 L4 scheme 을 열지 못하게 한다 |
| I7 | 값은 퍼센트 디코딩한다. 디코딩에 실패한 키는 없는 것으로 본다 | |

- Intent 객체 생성은 파서 결과를 옮기기만 하는 어댑터다 → 분기를 두지 않는다. 어댑터의 정상 경로는 TC#47 로 본다.

### 6.12 인증서 오류 처리 [FR#30] [NFR#5]

- `onReceivedSslError` 는 항상 `handler.cancel()` 을 부른다. 앱 소스에 `SslErrorHandler.proceed` 호출을 두지 않는다 → 단위 TC 가 소스를 읽어 고정한다 (TC#43).
- 기본 구현(`super`)도 `cancel` 이지만 명시한다 → 상위 동작이 바뀌어도 앱 코드만 보고 판단할 수 있다.

### 6.13 시작 안내·새 소식 판정 [FR#27] [FR#34]

순수 함수가 (기록된 versionCode 또는 없음, 현재 versionCode, 웹페이지·Tune 이 하나라도 있는지, 변경 안내가 있는 versionCode 목록) → (보여줄 것, 바로 쓸 기록)을 만든다. 위에서부터 처음 맞는 행이다.

| 조건 | 보여줄 것 | 기록 |
| --- | --- | --- |
| 기록 없음, 데이터 없음 | 시작 안내 | 닫을 때 현재 versionCode |
| 기록 없음, 데이터 있음 | 새 소식: 목록 중 현재 이하 전부. 하나도 없으면 없음 | 닫을 때 현재. 없음이면 바로 현재 |
| 기록 < 현재 | 새 소식: 목록 중 기록 초과 ~ 현재 이하. 하나도 없으면 없음 | 닫을 때 현재. 없음이면 바로 현재 |
| 기록 ≥ 현재 | 없음 | 바꾸지 않는다 |

- 새 소식의 버전은 최신부터 보인다.
- 기록 ≥ 현재 는 정상 배포에서는 같은 버전 재실행뿐이다. 다운그레이드 설치(개발 중)에서 기록을 낮추지 않는다 → 다시 올렸을 때 이미 본 새 소식이 반복되지 않는다.
- 태그 없는 개발 빌드의 versionCode 는 1 이다 (`spec_release.md`) → 목록의 어떤 버전도 1 이하가 아니므로 새 소식이 보이지 않는다.
- 데이터 유무는 판정 전에 DB 에서 한 번 읽는다.

### 6.14 끝에서 당겨 이동 판정 [FR#36]

순수 함수가 (상태, 터치 이벤트) → 다음 상태와 누를 쪽(위·아래·없음)을 만든다. 거리는 dp 다.

| 이벤트 | 다음 상태 |
| --- | --- |
| 터치 시작 | 시작점 기록. 위 후보 = 맨 위 && 위 가능, 아래 후보 = 맨 아래 && 아래 가능 (짧은 페이지는 둘 다) |
| 두 번째 손가락 | 후보 모두 지움 |
| 이동: 가로 거리 > 세로 거리, 가로 8dp 초과 | 후보 모두 지움 → 가로 밀기(캐러셀 등)를 당기기로 보지 않는다 |
| 이동: 이번 터치에서 가장 많이 당긴 거리보다 16dp 이상 짧아짐 | 후보 모두 지움 (취소) |
| 이동: 아래로 8dp 초과 | 아래 후보 지움 |
| 이동: 위로 8dp 초과 | 위 후보 지움 |
| 이동 (후보 남음) | 아래 거리 → 위 당기기, 위 거리 → 아래 당기기. 8dp 이상이면 안내 보임. 160dp 이상이 되면 그 시각·거리를 기록하고, 기록한 거리에서 8dp 넘게 움직이면 지금 시각·거리로 다시 기록, 160dp 아래로 내려가면 지운다 → 기록 시각은 "멈추기 시작한 때" 다 |
| 손 뗌 | 기록한 시각부터 0.3초 이상 지났으면 그 쪽을 누름(준비). 상태 초기화 |
| 취소 | 누르지 않음. 상태 초기화 |

- "위·아래 가능" 은 Tune 켜짐 && 오류 화면 아님 && 그 쪽 당기기 연결 있음이다.
- 맨 위·맨 아래는 터치 시작 때 WebView 가 그 방향으로 더 스크롤할 수 없는지로 정한다.
- 후보가 지워지면 그 터치가 끝날 때까지 되살리지 않는다 → 반대로 움직였거나 취소한 뒤의 당김은 새 터치에서만 동작한다.
